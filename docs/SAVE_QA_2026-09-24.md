# Markdown save safety QA — September 24, 2026

## Scope and evidence

This review targets loss of Markdown edits, not merely a successful save API
return value. Native tests run a disposable VS Code profile and vault with VS
Code's own autosave and Hot Exit disabled, so they cannot mask extension failures.
Assertions compare complete on-disk bytes with the intended note. Personal notes
and settings are not test fixtures.

Reference environment: macOS 27.0 (Apple silicon), VS Code 1.139.0, Node.js
26.8.2. Windows and Linux save tests are wired into release-validation CI, but
were not executed on those operating systems during this review.

The initial native run reproduced four failures: trailing text lost after rapid
switches, trailing text lost on immediate close, an unfinished property edit lost
on switching, and an unfinished table edit lost on closing. After the first fix,
earlier switching rounds survived but the final hidden tab still lost its tail.
This isolated iframe teardown, which can occur without blur/pagehide delivery,
as an additional cause. The regressions are retained in the native suite.

Repeated native Text Editor typing also reproduced a separate final-character
loss: VS Code delivered a save notification for an older disk snapshot after
publishing newer text to the extension host. The host's dirty flag became false
despite the missing final character on disk. The review therefore also tracks
actual content revisions and native-save progress rather than trusting the dirty
flag or save return value alone. Native stress runs compare full bytes, not that
flag.

The shutdown regression also injects another edit during the save started by a
flush. A flush now waits for its follow-up save instead of returning while a
timer still holds the final revision.

## Built-in Markdown Editor compatibility finding

Broader desktop QA also observed `continued` becoming `cotinud` while typing in
VS Code's built-in Markdown Editor. Inspection of the installed 1.139.0 provider
shows that same-document change notifications, including save-related dirty-state
changes, invalidate its edit epoch and send authoritative text back to its
webview. Edits from an older epoch are ignored. Instrumented A/B runs delivered
all ten keydowns: autosave-on produced 30 authoritative updates/epoch 30, versus
one update/epoch 1 with autosave off. Three short repeats in each condition
passed, so the loss is intermittent; those passing samples do not clear the
observed full-suite failure.

The owner approved temporary routing to this extension's Live Preview. Both
native-editor setting aliases now resolve to Live Preview. Direct native tabs
inside the local vault are handed off without rewriting document content, with a
compatibility notice. Extension autosave is suppressed while any native Markdown
Editor tab still owns the URI, including hidden/split tabs, and resumes after
the last native tab closes. The safeguard does not modify VS Code binaries or
control saves already in progress or initiated by VS Code or other extensions.
Failed routing is explicitly warned;
plain Text Editor remains available.

The handoff regression also caught a second native-editor issue: opening Live
Preview and then normally closing a dirty native tab reverted the shared working
copy, deleting an exact 57-character unsaved suffix. It reproduced after another
handoff even though the isolated case passed. A dirty-before-close check was
insufficient: an initially clean tab can receive edits after an asynchronous
close has been issued. The final guard therefore never programmatically closes
native tabs. Live Preview opens alongside an existing or explicitly requested
native tab, preserves the unsaved buffer, and warns that autosave remains paused.
The user must explicitly save and verify the document before closing the native
tab. Normal setting-based opens go directly to Live Preview without this extra
step. No forced save, revert, or private editor-replacement command is used.

## Corrections and safeguards

- Send normal edits without a typing-idle delay. Preserve a bounded latest draft
  before teardown instead of relying on a close event in the renderer.
- Finish accepted mutations in sequence even after the editor closes. Reopening
  a closed document revalidates canonical vault containment and the immutable
  original text before applying offsets.
- Track reopened TextDocument identities separately from closed instances and
  serialize writes to the same URI. Old cleanup callbacks cannot detach a newer
  document or let an older save overtake it.
- Check dirty state after a nominally successful save. Bound retries and report
  errors; a failing save participant cannot cause an endless write loop.
- Keep local pending text when external edits or a resync arrive. Do not apply
  authoritative offsets to an already locally modified buffer. Conflicts create
  recovery copies rather than automatic destructive merges.
- Commit valid active table/property drafts at Save and lifecycle boundaries.
  Invalid typed values are recovery-only and cannot replay diagnostic text into
  the original note. Explicit Save waits for outstanding edit batches.
- Preserve invalid property text when focus leaves the field, before a later
  body edit or widget redraw can replace the pending snapshot. Explicit Escape
  still cancels the field without creating an unwanted recovery copy.
- Preserve recovery copies in local VS Code workspace storage. They open as new
  unsaved documents, never as an overwrite of the original. Deletion requires
  confirmation; opening a copy does not discard it.
- If persistent recovery is full or unavailable, open the exact draft as a pinned
  untitled Text Editor document and require Save As. If creation/display fails,
  retain a bounded provider-owned emergency snapshot beyond the closing webview's
  lifetime, expose it in the recovery picker, and do not acknowledge memory-only
  retention as successful preservation.
- Cooperate with normal extension shutdown by draining pending edits/saves.

## Security and privacy review

Recovery message variants have exact-field runtime validation. Text and baseline
are each capped at the existing 20 MiB document limit; request IDs and flags are
validated. Snapshot messages replace one cached latest snapshot rather than
adding full documents to an unbounded queue. Mutations still use the bounded
serial gate; preservation/checkpoint operations have a separate concurrency cap.
No message supplies a filesystem destination. Source URI metadata comes from the
host-owned TextDocument. Recovery storage never reads or writes that URI.

The recovery store permits at most 20 entries and 60 MiB of serialized data,
including JSON escape expansion, with a bounded pending-operation budget. It
deduplicates identical content, publishes entries only after storage succeeds,
and never evicts old copies to make room. Malformed preexisting recovery storage
is reported and not overwritten. There is no new network, telemetry, command
execution, or Markdown rendering permission.

Emergency memory-only recovery has a separate 20-entry/60 MiB UTF-8 content
budget and a bounded editor-opening queue. It never evicts distinct snapshots to
admit another. Existing exact native copies are reused. Opening a fallback does
not use the source URI as a write target. Simultaneous failure of persistent
storage, native editor creation, and emergency capacity produces an explicit
failure warning; finite recovery storage cannot guarantee preservation then.

Recovery text can contain sensitive note content. It is stored locally,
unencrypted, outside the vault and remains until explicitly deleted. Review
workspace-storage retention alongside the vault's local backup policy.

Native scenarios cover continuous typing, rapid switching, immediate close and
reopen, Unicode/BOM/CRLF/trailing spaces, checkbox edits, table and property
commits and unfinished drafts, configuration-triggered webview rebuilds, slow save participants, undo/redo, native Text

quota failures, oversized edits, failed writes, stale document identities, and
serialization races. Generated native evidence is under the ignored
`test-results/save-durability/` directory and contains only disposable test notes.

## Limits

This does not establish zero data loss under every failure. A process kill or
power failure can occur before input crosses IPC or storage completes. VS Code
workspace state is not a cross-process transactional backup. Renderer recovery
state and local copies complement, but do not replace, an independent backup.
Other extensions can transform or reject saves. Table/property fields remain
drafts until committed; Escape intentionally cancels such input. Windows/Linux
behavior is not claimed as live-tested by this macOS QA run.
